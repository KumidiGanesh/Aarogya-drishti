# API

The REST API base path is `/api`. `GET /healthz` is an internal liveness check. `GET /api/health` is an operational readiness check that pings MongoDB and reports `database: "connected"` only after a successful database check. Responses use `{ "success": true, "message": "...", "data": {}, "meta": {} }`. Errors use `{ "success": false, "message": "...", "errors": [], "code": "..." }`. List responses include pagination metadata.

Swagger UI is served at `/api-docs/` and its OpenAPI 3.0.3 document is at `/api-docs/openapi.json`. The spec is generated from the endpoint tables below; request bodies use generic JSON/multipart schemas, so this UI is a route/role index and not a substitute for the endpoint-specific validation and behavior described here.

All admin routes require a valid access token and the `super_admin` or `admin` role. User-management reads require `users:read`; mutations require `users:manage`; report exports require the `export` permission. List endpoints return `page`, `limit`, `total`, and `totalPages` in `meta`.

Patient registration OTP requests accept `{ "mobile": "9876543210" }`; verification accepts `{ "challenge_id": "<challenge id>", "code": "<six digits>" }`. The `/api/patient` routes always use fixed patient purposes and do not accept a client-selected role. The self-registration endpoint `/api/patient/send-otp` and its `/api/auth/patient/send-otp` alias are demo-only: they require `NODE_ENV=development` and `PATIENT_DEMO_OTP_ENABLED=true`, return `demo_otp` and `delivery_mode: "demo"`, and never fall back to an SMS provider. Patient OTP sign-in and password recovery also use the configured demo code in development when the same flag is enabled; otherwise they use their configured delivery provider. If the registration demo gate is off or the server is not in development, registration returns `503 DEMO_OTP_DISABLED`. The fixed `PATIENT_DEMO_OTP_CODE` defaults to `123456`. Demo challenges are HMAC-hashed, expire after five minutes, enforce a 30-second resend cooldown, and are consumed after five incorrect attempts. Demo verification is unavailable in production. Successful registration verification returns a one-time registration token consumed only after account details and consent are provided. Patient password registration stores bcrypt hashes; password login and reset revoke prior sessions as appropriate.

Doctor registration submits the required email address with the profile details to `POST /api/auth/register`; email OTP is not required and the email is not marked verified. The doctor account remains inactive until an administrator reviews and approves the request. The registration request does not accept an email-verification token.

For local demonstration, add `NODE_ENV=development`, `PATIENT_DEMO_OTP_ENABLED=true`, and optionally `PATIENT_DEMO_OTP_CODE=123456` to the server environment. The registration API returns an error rather than sending SMS when demo mode is unavailable. Never put provider credentials in frontend variables.

Registration requires affirmative consent and a valid mobile number for patient login; otherwise it returns 422 or 400. A possible duplicate returns 409 with limited candidate summaries in `errors[0].candidates`; the caller may retry using `force: true` and a justification. Duplicate checks compare normalized patient details, including mobile number and village. Aadhaar is not required or shown in the UI; if an API caller supplies it, only the last four digits are retained. Full identifiers are never stored. Offline registrations remain queued for manual synchronization so the staff member can hand off the one-time password; plaintext passwords are held only in the response/UI memory and are not written to IndexedDB. A stable `client_uuid` makes retry safe and permits reissuing a still-unclaimed temporary password. Only the app shell and synthetic master catalogs are cached, not patient API responses. A revoked photo consent is checked by the reusable `requirePhotoConsent` middleware before future image-upload routes.

Appointment slots use doctor availability stored as weekly local-time (`Asia/Kolkata`) slot strings. Super Admins and Admins configure those real start times in doctor management; empty schedules expose no slots. The database unique index is the final concurrency guard; a duplicate conflict is returned as HTTP 409. The scheduled job checks due 24-hour and 2-hour appointment reminders every five minutes and writes in-app notification records. Referral files use the existing AES-256-GCM private-storage adapter; no public object URL or storage key is returned to the client.

The appointment directory's 39 facility names are user-supplied selectable labels, not independently verified facility status. Apply or refresh the development catalog with `npm run seed:facilities`; the command refuses to run when `NODE_ENV=production`, upserts by exact name, marks prior deterministic demo facilities inactive, and does not delete appointment records. No doctor assignments or availability are inferred by this catalog seed.

The appointment/referral client provides booking, slot selection, calendar/list views, reschedule/cancel dialogs, reminder preferences, referral inbox/tracker, status timeline, feedback, follow-up, admin counters, and authenticated document downloads. The catalog query modes above reuse the six specified endpoint paths rather than adding routes.

### Telemedicine Socket.IO signaling

The authenticated Socket.IO server is attached to the existing API server at `/socket.io`. Clients send the current access JWT in the Socket.IO handshake `auth.token` field; query-string tokens are not accepted. The handshake checks the same active user, refresh-token session, role, permission version, and `consultations:manage` permission as the HTTP API. Production connections require HTTPS/WSS directly or an explicitly trusted HTTPS-terminating proxy, and use the same `CORS_ORIGINS` allowlist as the API.

Supported client events are `call:initiate`, `call:accept`, `call:reject`, `call:end`, `call:resume`, `call:join`, `call:offer`, `call:answer`, and `call:ice-candidate`. The server emits `call:incoming`, `call:busy`, `call:missed`, `participant:joined`, `participant:left`, and corresponding call-state events only to authenticated participant rooms. Initiation requires the call-token secret and configured STUN/TURN relays; it returns a socket-bound participant token that expires after two minutes and temporary TURN credentials. The invitee receives separate participant and TURN credentials with `call:incoming`. TURN credentials use the coturn shared-secret REST format, are scoped to the authenticated user, expire after two hours, and are never persisted. `call:resume` issues fresh participant and TURN credentials after a socket reconnect. `call:join` rechecks the appointment, consent, call state, user identity, and token before room membership. SDP and ICE events are validated and relayed only within that authorized call room. A consultation becomes in progress only after both participants join. Ringing calls time out after 45 seconds; a call that is accepted but fails to establish both participants within 30 seconds is closed. Disconnects receive a 20-second reconnect grace period. Presence is stored as expiring per-socket records and is not included in call tokens or notifications.

`CALL_TOKEN_SECRET` and `TURN_SHARED_SECRET` must each contain at least 32 bytes. `STUN_URIS` and `TURN_URIS` are comma-separated URI lists; both must be configured, and TURN URIs must not include static credentials. TURN initiation credentials are generated server-side. Call initiation returns `503 CALL_SIGNALING_UNAVAILABLE` for a missing call-token secret and `503 ICE_SERVERS_UNAVAILABLE` for missing or invalid relay configuration. The browser client uses WebRTC without recording calls; actual connectivity requires a reachable STUN service and a coturn-compatible TURN service with the configured shared secret.

`GET /api/consultations` includes `call_signaling_configured`, a non-secret readiness boolean. The patient consultation page also calls `GET /api/consultations?availability=true` to list active doctors and route a selected audio/video visit into the existing appointment booking flow. The availability response does not return patient information.

### Existing route field extensions

These features intentionally reuse their specified endpoint paths; they do not add business routes:

- `entity` selects a supported entity in the existing admin API.
- `action` selects the operation for consultation and referral mutations, as specified in their endpoint rows.
- `include=requests` expands emergency-contact results with SOS request history.
- `summary=true` adds adherence aggregates to medicine-log history.
- `image_id` on `GET /api/screenings/:id` streams one authorized image instead of returning an object URL.
- `download=documentId` on `GET /api/referrals` streams one authorized, audited referral document.

Responses retain the standard success/error envelope. Paginated lists place `page`, `limit`, `total`, and `totalPages` in `meta`; error responses include a stable `code` and an `errors` array. Use the API tables for role scope, field extensions, consent requirements, and endpoint-specific constraints.
